# Feedback for World

Written from integrating World ID server-side verification for a per-request approval ("step-up") on 2026-11-06. We have **not** completed a live verification yet: it was blocked on creating a Developer Portal team API key, which needs a human login. What follows is what we hit while reading the docs and SDK.

1. **How `signal_hash` is computed is not documented where you need it.** The integration guide says "your backend should enforce the same value" but not how a signal becomes `signal_hash`, and the v4 verify API reference only gives its defaults (`0x0`). The verify endpoint takes no expected signal, so the backend has to do the check itself. We found the answer only by reading `@worldcoin/idkit-core` (`hashSignal`, exported at `/hashing`). A sentence and a link to that function in the guide would save every integrator this.
2. **Binding an approval to one request is the natural use of a signal, but the docs push you toward one-nullifier-per-action.** The docs say the same person plus the same action always gives the same nullifier and suggest `UNIQUE (nullifier, action)`. That is right for sign-up, and wrong for "approve this payment". It took reading the concepts page to infer that the signal is not an input to the nullifier. An explicit "approving many different things" pattern would help.
3. **The Developer Portal MCP quickstart writes a secret into the repo.** The documented command uses `--scope project`, which stores the `Authorization: Bearer api_...` header in a committed `.mcp.json`. For an API key that "grants access to the team's apps", local scope should be the default shown.
4. **Domain names disagree across sources.** The docs and MCP use `developer.world.org`, while the SDK README and several guides use `developer.worldcoin.org`. We could not tell which one to sign in to.
5. **The v4 verify reference is thin on what we need to fail closed.** It lists field names, but not what `environment` and `success` guarantee together, whether a proof can be re-verified (replay), or what the nullifier-reuse behaviour is. We added our own single-use check on the proof nonce.
6. **Good:** `signRequest` and `hashSignal` in the server package are small, typed and synchronous, which made a testable verifier easy to write. The simulator and the `staging` environment are what made it possible to design the production/staging separation we enforce.
